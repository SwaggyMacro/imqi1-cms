AI 写的代码注释常常过于冗长、解释自我（如「为什么要做这个网站」）、自吹（如「这一步非常巧妙」），甚至把每行实现细节都在注释里复述一遍。用户强偏好：**注释尽量简短、必要、信息密度高**。

**Why:** 注释应解释「为什么」或非显而易见的设计取舍，不应解释「做了什么」（代码本身就是答案）。冗余注释增加阅读负担、占行数、未来修改时要同步更新、容易过时且带来误导。

**How to apply:**

- 默认写**自解释**代码（好的命名 + 简短结构），不写解释"做什么"的注释
- 只在以下情况写注释：
  - 解释**非显而易见的设计取舍 / why-not**：为什么不用方案 A、为什么有这段 hack
  - 标记**已知坑 / 长期约束**：跨模块约束、版本兼容、必须这样做否则会出 bug
  - 说明**业务语义**：变量/字段在业务上的含义（代码命名无法表达的）
- 注释长度：**每条注释最多一行**（2026-09-14 用户明确的硬约定，适用于整个项目，含 `.env` / `docker/` 等配置文件）。一行讲不完，就说明这段要么不该有注释、要么该拆进代码/记忆。**不要用多行注释块解释一件事**——需要展开的长知识写进 `.claude/memory/`，不写在代码里（用户 2026-09-14：「记忆我们以后不写在代码里，全在专门的记忆中」）。相邻的两条独立单行注释可以（如 stage 分隔线 + 其下说明），但一件事不许占两行
- 不要写「这是什么/做了什么」的注释——重构时这些注释最碍事
- 不要写「自我表扬」式注释（「这个方案很优雅」「巧妙之处在于…」）
- **配置文件 / 类型定义里的字段注释，只描述字段自身，不写「消费它的地方会怎么处理」**——如「静态资源此处写裸路径，由 `publicAsset` 在生产环境补 CDN 前缀」。用户 2026-09-14 原话：**「site.config.ts 和 site-config.ts 内部不要写自动由 publicAsset 补全」**。

**Why:** 注释应解释「为什么」或非显而易见的设计取舍，不应解释「做了什么」（代码本身就是答案）。冗余注释增加阅读负担、占行数、未来修改时要同步更新、容易过时且带来误导。字段注释里写消费行为还有额外一层错：把「定义」耦合到某一个「消费点」，而消费点常常不止一个、实现还不一样（本仓库静态资源的构建期走 `publicCdnAsset`、运行期走 `publicAsset`），写一句就错一半，且日后改消费点不会想到回来改注释。见 [[site-config-values-stay-bare]]。
